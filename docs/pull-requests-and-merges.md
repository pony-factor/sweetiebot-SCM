# Pull requests, Kefania, Lindsey and review safety

## Creation and publication

**New PR** starts a dedicated Sweetiebot PR workspace and ChatGPT drafting/research flow. The local **Kefania** runner supplies repository context, diff, actual head/base, and publication handoff. Opening a chat or creating a draft does **not** itself create a remote PR. `sweetiebot.autoPublishPullRequests` defaults to `true` in the manifest for **completed eligible drafts**; local settings and successful authorization control whether publishing actually happens. Optional independent pony-profile research is separate from PR description drafting; it includes a sourced **Important moments** section with timestamped links into verified full episodes when available. The existing confirmation window renders those Markdown links locally, and the research is not copied into the PR description.

After opening an upstream or personal PR yourself, use **Sweetiebot: Post Change Summary to Existing Pull Request** from the Command Palette, or **Post change summary** beside an open PR in Lindsey. Paste the exact upstream PR URL when prompted. The editable Markdown form uses verified commit subjects and changed paths as a starting draft; it does not claim an AI code review. After you confirm, Sweetiebot re-reads the open PR head and posts a new top-level Conversation comment through your locally authenticated `gh` CLI. This works for public upstream contributions without a Kefania or Lindsey App installation, provided your GitHub account can comment. A same-author, same-head marker prevents duplicates. No PR title, description, branch, or commit is modified.

PR opener, Git commit author/committer, co-author trailer and review commenter may be different identities. See [distinct GitHub App setup](distinct-github-apps.md).

## Merging and blockers

**Sync to main** refreshes the tracked default branch before incorporating its changes. With separate GitHub Apps configured, the Lindsey bot is both author and committer of new sync commits and authenticates pushes and routine sync report comments; an App failure never falls back to the user's identity. Existing commits and Git signing settings are preserved. For conflicts, **Resolve and sync with Lindsey** opens the existing local resolver's proposal diffs. **Apply and sync with Lindsey** explicitly approves staging those resolutions, committing and publishing as the same App. Cancelled or stale proposals leave the branch uncommitted. This resolver still requires a discoverable `lindsey-sync` checkout and its configured resolution endpoint.

**Squash and Merge**, **Merge All**, and selected batch actions use guarded GitHub/Kefania/Lindsey surfaces. Dashboard selection or submitting a ChatGPT prompt is **not** a verified merge. Recheck every PR's **live head SHA**, **actual base** (not assumed `main`), state, checks, rules, reviews, conflicts, attribution and stack dependencies. Merging an earlier PR can advance another PR's base and invalidate previous checks: reassess before continuing.

Kefania reads `commit.gpgsign` from the selected local checkout. When it is enabled, the default squash action creates and verifies a locally signed, one-parent squash instead of using GitHub's REST squash endpoint, which does not use the local signing key. The workflow force-updates **only the PR head**, using an exact `--force-with-lease`, then advances an unprotected base with a normal fast-forward push. It refuses protected or ruleset-controlled bases, dependent PRs, failed checks, and signatures GitHub does not verify; it never force-pushes a base branch. If signing is not configured, the normal GitHub-native squash path remains unchanged.

Lindsey checks the current PR head to distinguish **Checks in progress** (queued or running CI) from blue **Checks failing** (verified failed CI), rather than treating GitHub's broad `unstable` mergeability state as proof of a failure. Red **Blocked** (merge rules or unverified restrictions) and **Conflict** (merge conflicts) remain separate; checks must still pass before merging.

The sync-commit filter normally omits routine `Sync brach/branch to main` entries from summaries without discarding legitimate author credits. Automatic Lindsey merges resolve conflicts in a disposable integrated tree without updating the source PR branch. Clean human-owned PRs use GitHub's native squash. Conflicted PRs may instead require a verified two-parent integration commit into an unprotected destination, preserving the original head and its ancestry; this is not a one-parent squash. Protected bases and active branch rules cannot be bypassed, and the maintainer can use Sweetiebot Sync explicitly if required. Deterministic CI failures are deferred to dedicated repair rather than another synchronization. Lindsey opens one repair task per verified failing PR head by default; the maintainer can disable Auto-fix failing CI without relaxing merge checks. Defer materially ambiguous behavior; do not silently bypass protections.

The optional external Lindsey runner is discovered by [`extension/lindsey-bulk-merge.js`](../extension/merge/lindsey-bulk-merge.js). **There is no local `scripts/bulk-merge.js` in Sweetiebot.** Its remote script and deployment must be managed separately.

## One-click Lindsey handoffs and bulk conflict resolutions

With separate GitHub Apps enabled, the merge and bulk-handoff executors use the configured Lindsey installation for writes, even when launched from a signed-in user session. New conflict-fix, branch-sync and local integration commits use Lindsey as both author and committer. Existing commits retain their original authors and history; a squash that consolidates original human work retains the verified human author while new local commits use the App committer. Local integration messages retain the original human's credit. Signing settings remain in effect. App authentication or identity failures stop the operation without publishing as the user. Web repair actions also use the local App handoff in this mode.

**Apply with Lindsey** is the primary action: ChatGPT returns one compact link and a brief explanation, not a raw Git diff. Normal handoffs use a gzip/Base64URL fragment. A short SHA-256 link and a collapsed compressed transport payload are reserved for exceptionally large responses that cannot fit the normal link; only the nonce-scoped local bridge stages those bytes. The local executor verifies the selected PR snapshot before changing Git, and a failed transfer does not partially apply the fix.

When many files or large files conflict, the assistant should prefer **compact conflict hunks** rather than reproduce entire unified diffs. Set `patch: null` and supply `resolutionHunks`, each naming an affected PR file and ordered zero-based Git conflict regions. A region can choose `ours` (current base), `theirs` (PR feature), `both-ours-first`, `both-theirs-first`, or `custom` with the complete replacement text for that region. Include a specific per-file decision. The local isolated Git merge preserves nonconflicting changes; it independently verifies actual conflicted files, hunk counts, and optional expected sides. Incomplete, stale, or unrelated resolutions fail closed.

Complete text patches remain supported when a compact hunk is unsuitable. Resource limits reject oversized input explicitly; no patch is silently truncated. Binary, secret-bearing, symlink, submodule, rename, and unrelated path changes remain prohibited. After execution, branch-only repairs append commits to the selected PR branch without force-pushing or changing `main`.

## AI reviews and authorization boundaries

**Respond to AI Code Review** selects one unresolved inline thread, waits for a published relevant single-commit change, asks a local model to assess the exact diff, posts a bounded explanation in the **original thread**, then resolves it if substantiated. See [full procedure and safeguards](ai-review-reply.md). A general PR conversation comment is not the same operation.

In optional separate-App mode, Lindsey may read PRs/checks/diffs via a repository-scoped installation token; write operations, merges, pushes and reactions still require appropriately authorized accounts. Missing credentials **fail closed** without impersonation. See [App identity configuration](distinct-github-apps.md).
